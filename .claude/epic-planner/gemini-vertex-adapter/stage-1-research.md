# Research: Vertex AI Gemini Adapter (SA-authenticated, dual-path with API key adapter)

## Summary

The gateway has one working Gemini adapter today (`proxy/app/providers/gemini.py`), talking to the public Gemini Developer API (`generativelanguage.googleapis.com`) with an `x-goog-api-key` header. The task is to add a second, parallel path to the same Gemini models via Vertex AI, authenticated with an impersonated GCP service account (SA) instead of an API key, and to let admins/tenants/callers choose which path a request takes — without breaking the existing API-key path.

Internal repo research (already complete before this document) confirms:

- The gateway's provider-adapter pattern is consistent across `openai`, `anthropic`, `azure-openai`, `bedrock`, `ollama`, `generic` — each a module with `make_client()` + request/response translation functions in `proxy/app/providers/`.
- `config/models.yaml` has a live bug: the Gemini entries are tagged `provider: google`, but `proxy/app/routing.py`'s prefix map and `proxy/app/provider_capabilities.py`'s capability dict both key off `"gemini"`. `proxy/app/main.py` line 486 papers over this with a shim: `capability_provider = "gemini" if provider == "google" else provider`. This must be fixed, not extended, by the new design.
- Selection precedent already exists in two working forms: `config/tenants.yaml` has a per-tenant `default_provider` field used today; `policies/llm/provider_override.rego` already role-gates a `x-gateway-provider` header override permission-checked as `gateway:provider_override:<provider>`. Both are live, tested mechanisms, not new inventions.
- `proxy/app/protocol_types.py` shows Gemini is never in `native_providers` (`frozenset({"generic", "ollama", "openai"})`) — Gemini requests always go through the translated-chat dispatch path in `main.py`, not the native passthrough path. A Vertex-backed Gemini path would structurally sit in the same translated-chat call site, which is what makes sharing translation code between the two Gemini adapters realistic.
- `scripts/google_adc_keychain.py` and `docker-compose.google-dlp.yml` already establish the house convention for GCP SA auth: impersonated ADC JSON only (never a raw SA key file), validated to have `type=impersonated_service_account` with `source_credentials.type` in `{authorized_user, external_account}`, a background credential-sentinel container that polls identity and writes a metadata-only (never-the-token) status file, and a consuming service that fails closed when that status is stale. This is GOVERNANCE-side today (`docker-compose.google-dlp.yml`, `GOOGLE_DLP_*` env vars), for the Google DLP PII backend — a different service than the proxy, but the same conventions apply.
- `proxy/app/config.py`'s `Settings` class (used by the **proxy** service, where the adapters live) currently has no Google-Cloud-specific fields at all beyond `gemini_api_key: str = ""` — the `GOOGLE_DLP_*` settings live in the **governance** service's own config, not here. So there is no literal field-name collision risk, but the env var naming should still use a distinct prefix (`GEMINI_VERTEX_*`) for clarity, even though both may point at the same GCP project (`prod-meal-mentor`).
- `proxy/app/providers/errors.py`'s `sanitize_upstream_error()` is the shared error-sanitization path all adapters must return through; 401/403/500/502/503/504 are always given an opaque generic message today. Vertex's distinct auth-failure modes need to be classified into this scheme, not bypass it.
- `proxy/pyproject.toml`: `google-genai==2.17.0` is a **dev-only** dependency today, used solely by `proxy/tests/test_official_sdk_contracts.py` to assert `GEMINI_GENERATE_CONFIG_FIELDS` (a hand-maintained list in `provider_capabilities.py`) stays in sync with the real `google.genai.types.GenerateContentConfig.model_fields`. It is not a runtime dependency. No `google-auth` or `google-cloud-*` package is a dependency (runtime or dev) today.
- `policies/llm/authz.rego` gates PHI/BAA traffic to `phi_approved_providers := {"azure-openai", "bedrock"}` only. Neither existing Gemini path, nor a new Vertex path, is on that list — out of scope for this feature, worth a Non-Goals line.

External research (via a background research agent verifying live Google Cloud documentation, REST Discovery documents, and `google-auth`/`google-genai` source — **not** relying on training-data memory) is written in full at `.claude/epic-planner/gemini-vertex-adapter/deep-research.md`. Highlights relevant to the design:

- **Endpoint**: regional pattern `https://{location}-aiplatform.googleapis.com/v1/projects/{project}/locations/{location}/publishers/google/models/{model}:generateContent` is current and correct. A global endpoint also exists: same path shape, but hostname `aiplatform.googleapis.com` (no region prefix) and `locations/global` in the path — Google's own stated purpose is reducing 429s, at the cost of not controlling which region actually processes the request.
- **Auth**: Vertex requires `Authorization: Bearer <token>` (OAuth2, scope `https://www.googleapis.com/auth/cloud-platform`), obtained via Application Default Credentials — fundamentally different from the Developer API's `x-goog-api-key` header. `google.auth.default()` loads an impersonated-service-account ADC JSON automatically, no manual credential construction needed. Token refresh (`credentials.refresh()`) is synchronous/blocking; there is no working async path for this credential type in `google-auth` (`google.auth.aio` explicitly does not support `impersonated_service_account`). The standard mitigation is wrapping the refresh call in `asyncio.to_thread`. `google-auth`'s own `.expired`/`.valid` properties already build in a ~3m45s refresh margin — no custom skew logic needed. Package: `google-auth`, current version 2.56.3, `requires_python >= 3.10`.
- **Body-shape parity is real but not 100%.** Concrete divergences that adapter code must handle: (1) Vertex has **no `model` field in the JSON body at all** — the model is only in the URL path as a fully-qualified `projects/{project}/locations/{location}/publishers/google/models/{model}` resource name, vs. the Developer API's bare `models/{model}`; (2) `finishReason` enums differ — Vertex has a `MODEL_ARMOR` value the Developer API lacks, the Developer API has five values (`LANGUAGE`, `TOO_MANY_TOOL_CALLS`, `MISSING_THOUGHT_SIGNATURE`, `MALFORMED_RESPONSE`, `ESCALATION`) Vertex lacks; (3) the `promptFeedback.blockReason` "unset" sentinel is spelled differently on each API (`BLOCKED_REASON_UNSPECIFIED` on Vertex vs `BLOCK_REASON_UNSPECIFIED` on the Developer API) — an easy silent bug if normalization code does an exact-string match; (4) `HarmCategory` safety-setting enums only overlap on four values (`HATE_SPEECH`, `DANGEROUS_CONTENT`, `HARASSMENT`, `SEXUALLY_EXPLICIT`); (5) usage/token-count field names (`promptTokenCount`, `candidatesTokenCount`, `totalTokenCount`, etc.) **are identical** on both APIs — this part of the existing translation code can likely be reused as-is.
- **Errors**: all Vertex errors use the standard `google.rpc.Status` envelope. Two independent 403 failure modes exist for impersonation-based auth — one when the impersonation grant itself is missing (fails at `iamcredentials.googleapis.com`, before Vertex is ever called), one when the impersonated SA reaches Vertex but lacks `roles/aiplatform.user` — these need different remediation messaging and should be distinguished by which upstream service raised the error. 404 "model not found" is deliberately ambiguous in Vertex (folds together "doesn't exist," "not available in this region," and "no access" into one message) — region/model availability should be validated client-side against a known table, not parsed from the error text. 429 bodies use a legacy `errors[]` shape (`reason: "rateLimitExceeded"`), not the newer `QuotaFailure` shape.
- **SDK unification**: Google now ships one SDK, `google-genai`, that can target either backend via a `vertexai`/`enterprise` constructor flag. The research explicitly did not recommend an architecture (that's this project's job) but confirmed the SDK is a real, current, viable option, separate from hand-rolling httpx + `google-auth`.
- Several items are flagged **UNCERTAIN** by the researcher (14 total, listed in `deep-research.md`) — none are blocking for design decisions, but should be spot-checked (e.g., with a live smoke test) before the Vertex adapter ships, particularly the exact `alt=sse` streaming framing and the precise 403 `reason` string for a missing `roles/aiplatform.user` grant.

## Recommended Approach

**Two open design questions were explicitly flagged for a recommendation, plus one implicit dependency question surfaced by the research. All three recommendations below are proposals for the SPEC stage, not yet approved.**

### 1. Module structure: two thin provider modules sharing a translation core

Given the body-shape divergences above are real but modest (model addressing, finish-reason enum membership, one enum-sentinel spelling difference, safety-category subset, a handful of Vertex-only/Dev-API-only fields) — not a full schema rewrite — recommend:

- Keep `proxy/app/providers/gemini.py` as the Developer API adapter, unchanged in its public surface.
- Add `proxy/app/providers/gemini_vertex.py` as a new, separate adapter module (own `make_client()`, own `chat_completions()`) — because the two paths have genuinely different client construction (API key vs. OAuth2 credential object + token refresh), different base URLs, and different model-addressing rules, which would otherwise force one module to branch on "which backend am I" at nearly every function.
- Extract the ~90%-shared request/response translation logic (content/parts mapping, generationConfig mapping, tool/function-calling mapping, the shared subset of finish reasons and safety categories, usage-metadata mapping) into a shared internal module, e.g. `proxy/app/providers/_gemini_common.py`, parameterized by a small per-backend "dialect" object (model-path builder, finish-reason map, safety-category allowlist, base-URL/auth-header builder) rather than duplicating ~200 lines of near-identical mapping code twice.
- This avoids both extremes flagged in the task: one bloated module with pluggable auth+base_url+naming (harder to test, harder to reason about which backend a given code path affects) vs. fully duplicated modules (drifts silently, e.g. someone fixes a mapping bug in one and not the other).

### 2. Selection mechanism: layer the three real options, using the existing precedence order

`resolve_provider()`'s existing precedence — header override → exact model match → prefix inference → tenant default — is proven and already tested. Recommend using all three existing mechanisms, not inventing a fourth:

1. **Fix the naming bug first.** Rename `config/models.yaml`'s Gemini entries from `provider: google` to `provider: gemini`, and remove the `main.py:486` shim (`"gemini" if provider == "google" else provider`). This is a prerequisite, not an add-on — the new provider value needs a clean, non-confusing sibling name.
2. **New distinct provider value for Vertex**: `gemini-vertex` (not `google-vertex` or `vertex`, to stay visually paired with the now-corrected `gemini` value in routing/capability code).
3. **Explicit model-catalog entries** (primary mechanism): because a single model id can't map to two providers in one `models.yaml` dict, add explicit Vertex-routed model entries (e.g. a `-vertex` suffixed alias) so a caller can request the Vertex path by model id alone, discoverable in the catalog like any other model.
4. **Per-tenant default** (`config/tenants.yaml`'s existing `default_provider` field): a tenant can be defaulted to `gemini-vertex` so that bare `gemini-*` prefix-inferred requests resolve to the SA-backed path without every caller needing to know the `-vertex` alias.
5. **Role-gated header override** (`x-gateway-provider: gemini-vertex`, already implemented in `policies/llm/provider_override.rego`): works automatically once `gemini-vertex` is a recognized provider value — needs a policy/test update, not new mechanism code.

### 3. Dependency: hand-roll httpx + `google-auth`, do not adopt `google-genai` as a runtime dependency

This wasn't one of the two explicitly-flagged decisions, but the research surfaced it as a real fork. Recommend hand-rolling (httpx + new `google-auth` runtime dependency), not adopting `google-genai` as a runtime SDK, because:

- Every other adapter in this gateway (`openai`, `anthropic`, `azure-openai`, `bedrock`, `ollama`) is a hand-rolled httpx module with explicit translation functions — adopting a full SDK for exactly one provider breaks that consistency and adds a second, structurally different way adapters are built.
- The existing test suite (`test_adapters.py`) mocks upstream calls with `httpx_mock` matching exact URLs/headers — this pattern extends directly to a hand-rolled Vertex adapter and does not extend cleanly to a wrapped third-party SDK client.
- `sanitize_upstream_error()` needs precise control over what error detail is/isn't surfaced; a hand-rolled httpx call preserves that control directly, where an SDK exception hierarchy would need its own translation layer anyway.
- The now-fully-documented field-level parity/divergence table (this research) makes hand-rolling low-risk — the "unknowns" that usually justify pulling in an SDK (undocumented body shape) are resolved.
- `google-genai` stays exactly where it is today: a dev-only dependency for contract testing (`test_official_sdk_contracts.py`), which can optionally be extended to also assert the Vertex-side field lists stay in sync with `google.genai.types`, without becoming a runtime dependency.
- New runtime dependency to add via `uv add`: `google-auth` (2.56.x). This is the only new runtime dependency this feature requires.

## Technology Options

| Concern | Option | Recommendation |
|---|---|---|
| Vertex REST client | Hand-rolled httpx vs. `google-genai` SDK | Hand-rolled httpx (see above) |
| Auth token acquisition | `google-auth` (`google.auth.default()` + `impersonated_credentials`) vs. hand-rolled OAuth2 flow | `google-auth` — it already auto-detects and loads impersonated-SA ADC JSON with zero manual credential construction |
| Async-safe token refresh | Wrap sync `credentials.refresh()` in `asyncio.to_thread` vs. `google.auth.aio` | `asyncio.to_thread` — `google.auth.aio` does not support `impersonated_service_account` credentials at all |
| Endpoint | Regional (`{location}-aiplatform.googleapis.com`) vs. global (`aiplatform.googleapis.com`, `locations/global`) | Make it configurable per deployment (setting), default to regional for predictable data-processing location; document the global option's 429-reduction tradeoff for ops to opt into later |
| Module structure | One module, pluggable auth/base_url/naming vs. two modules sharing a translation core | Two modules + shared `_gemini_common.py` core (see above) |
| Selection mechanism | Model-catalog entry vs. tenant default vs. header override | All three, layered on existing `resolve_provider()` precedence (see above) |

## Risks & Considerations

- **Silent enum mismatches.** The `blockReason` sentinel spelling difference (`BLOCKED_REASON_UNSPECIFIED` vs `BLOCK_REASON_UNSPECIFIED`) and the non-overlapping `finishReason`/`HarmCategory` enum members are exactly the kind of bug that passes tests against one backend and silently misbehaves against the other. Translation-core tests must exercise both dialects explicitly, not just one with the other assumed "close enough."
- **Two independent 403 causes for one HTTP status.** A missing impersonation grant (`iamcredentials.googleapis.com`) and a missing `roles/aiplatform.user` grant (`aiplatform.googleapis.com`) both surface as 403, but need different operator remediation. The adapter should classify by which upstream host/service raised the error where possible, and `sanitize_upstream_error()` still needs to keep the caller-facing message generic per existing policy (401/403/etc. stay opaque) — the distinction is for internal logging/alerting, not the client-facing error body.
- **404 ambiguity.** "Model not found" on Vertex conflates missing model, wrong region, and missing access into one message — region/model availability should be validated against a maintained table in the model catalog rather than parsed from Vertex's error text.
- **Token refresh is blocking.** Every outbound Vertex call needs a valid token; the refresh call must never run on the event loop thread. This needs a deliberate async wrapper (`asyncio.to_thread`) and a cached-credentials-object-per-process pattern (not fetching fresh credentials per request), analogous to how `make_client()` already returns a long-lived client for other providers.
- **Credential-sentinel reuse question.** DLP's credential sentinel (`docker-compose.google-dlp.yml`) lives in governance and monitors DLP's own impersonated identity. The proxy service is a different container with its own lifecycle; whether the Vertex adapter needs its own sentinel, can share DLP's sentinel/status file (if same SA), or should just rely on `google-auth`'s built-in `.valid` check plus adapter-level error handling (simpler, no new background process) is a real open question for the SPEC. Given the proxy already fails a request cleanly through `sanitize_upstream_error()` on a 401/403, and Vertex calls are synchronous per-request (unlike DLP's continuous background need), recommend **not** building a parallel sentinel for the proxy — rely on `google-auth`'s in-library validity check and per-request error handling instead. This should be confirmed at the approval gate.
- **14 UNCERTAIN items from the research** (full list in `deep-research.md`) are non-blocking for the SPEC but should inform test-writing — most notably: exact `alt=sse` streaming framing (recommend a live smoke test before finalizing the SSE parser), and the exact 403 `reason` string for a missing `roles/aiplatform.user` grant (currently inferred by analogy, not directly confirmed).
- **PHI/BAA scope.** Neither Gemini path is BAA-approved (`policies/llm/authz.rego`'s `phi_approved_providers` doesn't include either). This feature does not change that; explicitly a non-goal.
- **Same GCP project as DLP likely.** `prod-meal-mentor` is the probable shared project. Config field names must stay distinct (`GEMINI_VERTEX_*` prefix) even if the project ID value happens to match `GOOGLE_CLOUD_PROJECT` used by DLP, to keep the two services' configuration independently auditable and changeable.

## Alternative Approaches

- **Single unified adapter module with backend as a runtime parameter** (rejected as primary approach) — considered, but rejected in favor of two-modules-plus-shared-core: a single module handling both backends would need `if backend == "vertex"` branches scattered through client construction, auth, URL building, and error classification, making it harder to reason about which backend a change affects and harder to test the two paths in isolation.
- **Full duplication (two independent adapters, no shared core)** (rejected) — considered and rejected: the ~90% field-mapping overlap (content/parts, generationConfig, tool calling, usage metadata) would drift silently between the two copies over time, exactly the kind of bug the enum-divergence risk above already warns about.
- **Adopt `google-genai` as the runtime client for both Gemini paths, replacing the existing Developer API adapter too** (rejected) — considered since it would reduce total code, but rejected because it's a much larger-scoped, riskier change (rewriting a working adapter) than this feature's ask, breaks the gateway's consistent hand-rolled-httpx pattern across all providers, and complicates the existing `httpx_mock`-based test suite. Could be revisited as a separate, independent proposal later.
- **Single model-catalog id with backend resolved purely by tenant default / header override (no explicit `-vertex` model alias)** (rejected as sole mechanism) — considered as a simpler selection mechanism, but rejected as the *only* mechanism because it removes explicit, discoverable per-request control — a caller who wants the Vertex path specifically would have no way to ask for it by model id alone, only via tenant config or a role-gated header. Kept as one of three layered mechanisms instead of the only one.
- **New dedicated credential-sentinel container for the proxy, mirroring DLP's** (rejected, pending approval-gate confirmation) — considered for symmetry with the DLP precedent, but rejected as likely-unnecessary complexity for a synchronous, per-request credential need versus DLP's continuous background need. Flagged in Risks for explicit confirmation rather than silently decided.
