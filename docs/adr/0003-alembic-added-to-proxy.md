# Proxy gets its own Alembic instance, separate from governance's

Proxy has never had schema-migration tooling — `api_keys`, `tenants`, `users`, and `provisioner_state` are all created by idempotent `CREATE TABLE IF NOT EXISTS` statements in `scripts/provision.py`, with no version history or rollback. The new `usage_log` and `pricing` tables need real schema evolution (indexes tuned, columns added, rates re-modeled), so we're adding Alembic to the proxy service, mirroring governance's existing setup (`governance/alembic.ini`, hand-written raw-SQL migrations, no ORM, a `migrate` Compose service). We considered a single shared Alembic instance across both services instead, but proxy and governance already own disjoint sets of tables in the same physical database, and a shared migration history would blur that ownership boundary; two independent instances keep each service in control of its own schema, at the cost of two separate migration setups instead of one. `api_keys`/`tenants`/`users`/`provisioner_state` are left as-is in `provision.py` — this only applies to the new tables going forward.
