# Pre-Build Gaps — LLM Governance Gateway

These are open questions and missing design decisions identified during planning. They must be
researched and resolved before implementation begins. The goal is to turn each gap into a
concrete decision added back to the plan.

## Project Context

We are building an enterprise-grade LLM governance gateway as a portfolio project. It sits
between consuming applications and external LLM providers (OpenAI, Anthropic, Gemini, Ollama),
intercepting every request to enforce data compliance, PII redaction, content policy, and
access control.

**Architecture summary:**
- **Reference Proxy** (FastAPI, port 8741): OpenAI-compatible API surface. Handles auth,
  rate limiting, calls the governance engine, routes to provider adapters.
- **Governance Engine** (FastAPI, port 8742): Runs PII detection (Presidio), harm scanning
  (llm-guard), OPA policy evaluation, and writes an append-only audit log to Postgres.
- **OPA sidecar** (port 8181): Policy decisions in Rego (model access, data classification).
- **Redis**: Rate limiting (sliding window, atomic Lua).
- **Postgres**: API keys (`prefix + bcrypt_hash`), audit log (metadata only, no PII text).

The proxy exposes an OpenAI-compatible API so existing client code works without modification.

**IaC principle (stated by the project owner):** All configuration must be declared as code.
Manual processes — creating keys, granting permissions, setting up tenants — must be eliminated.
Everything must be reproducible from code.

## Gap 1: User Provisioning — No IaC Design

### What's missing

There is no defined mechanism for provisioning users and tenants. The plan specifies that
`POST /v1/keys` (admin only) issues gateway API keys, but:

- There is no `tenants.yaml` or `users.yaml` schema defined
- There is no `make provision` or equivalent IaC workflow
- There is no bootstrap admin key mechanism (chicken-and-egg: you need an admin key to
  create other keys, but there's no first admin key)
- There is no definition of who can create tenants, who can assign roles, or what the
  provisioning workflow looks like for a new user

### What needs to be researched

1. **Declarative provisioning format**: What does a `tenants.yaml` / `users.yaml` look like?
   What fields does a tenant need (id, name, allowed models, rate limits, pii_action)?
   What fields does a user need (id, tenant, roles)?

2. **Bootstrap admin key**: What is the standard pattern for creating the first admin
   credential in a gateway/proxy system? Options include:
   - `BOOTSTRAP_ADMIN_KEY` env var (one-time use, disabled after first startup)
   - `make seed` target that writes directly to Postgres and prints the key
   - A one-shot `gateway-admin` CLI command
   What do comparable systems (LiteLLM, Kong, Traefik) use?

3. **Key distribution**: Once a key is generated by the provisioning workflow, how does the
   user receive it? Options include:
   - Written to a local file by `make provision`
   - Stored in a secrets manager (AWS SSM Parameter Store, HashiCorp Vault, Fly.io secrets)
   - Printed once to stdout (like Stripe's "copy this now" pattern)
   What is the right approach for a portfolio project that also demonstrates production thinking?

4. **Role assignment IaC**: The OPA policies enforce `tier2-access` roles. Where is role
   assignment declared? In `users.yaml`? In OPA data documents? How does a role change get
   applied without restarting services?

### Decision required

- Schema for `tenants.yaml` and `users.yaml`
- Bootstrap admin key pattern
- Key distribution mechanism
- Role assignment location and update workflow

## Gap 2: Provider Routing — OpenAI SDK Incompatibility

### What's missing

The plan routes requests to provider adapters based on a `provider` field in the request body.
The OpenAI SDK (and every OpenAI-compatible client library) does not send a `provider` field
— it sends only `model`. A user calling the gateway with a standard OpenAI client has no way
to specify the provider.

Example problem:
```python
client = OpenAI(base_url="http://gateway:8741/v1", api_key="gw-...")
# This sends {"model": "claude-sonnet-4-6", "messages": [...]}
# The gateway doesn't know if this should go to Anthropic or a generic endpoint
response = client.chat.completions.create(model="claude-sonnet-4-6", messages=[...])
```

### What needs to be researched

1. **Model-name inference**: Can provider be reliably inferred from model name prefixes?
   - `gpt-*`, `o1-*`, `o3-*` → OpenAI
   - `claude-*` → Anthropic
   - `gemini-*` → Gemini
   - What are the edge cases? What happens when a new model doesn't match a known prefix?

2. **Tenant-default provider**: Should each tenant have a configured default provider in
   `tenants.yaml`? This means the tenant is "pinned" to one provider unless they explicitly
   override. How do comparable gateways (LiteLLM, PortKey) handle this?

3. **Model routing table**: Should the gateway maintain a `models.yaml` that maps model names
   to providers? This is explicit and auditable but requires maintenance. LiteLLM uses a
   `config.yaml` with explicit model-to-provider mappings. Is this the right pattern?

4. **`GET /v1/models` response**: What should the gateway return here? The union of all
   configured models across all providers? Or only models the calling user is allowed to use
   (per OPA policy)?

### Decision required

- Primary routing mechanism: model-name inference, tenant default, or explicit routing table
- Fallback behavior when model name doesn't match any known prefix
- Whether `GET /v1/models` is user-scoped (filtered by OPA) or global

## Gap 3: User-Facing Error Messages — Not Actionable

### What's missing

When the governance engine blocks a request, the user receives a 403 with a `violations` array.
The messages are accurate but not actionable. The user cannot self-serve to understand what
they need to do differently.

**Current response:**
```json
{
  "error": {
    "code": "policy_violation",
    "violations": [
      {"policy": "phi-to-external-provider", "reason": "PHI cannot be sent to unapproved external providers"}
    ]
  }
}
```

**Missing:**
- What PHI was detected (entity type, not the actual text)
- What providers are approved for PHI (so the user knows where to route instead)
- What the user's current roles are
- What role they'd need to access a blocked model

Same problem with rate limits:
- 429 response has no `Retry-After` header (OpenAI SDK's retry logic requires this)
- No indication of current usage vs. limit
- No indication of when the window resets

### What needs to be researched

1. **Error response schema**: What fields should a governance violation response include
   to be maximally actionable? Research how other API gateways (Kong, AWS API Gateway,
   Apigee) structure policy-violation errors.

2. **`Retry-After` header**: What value should this be? The window reset time? A fixed
   backoff? How does the OpenAI SDK use it, and what does LiteLLM return?

3. **Rate limit headers**: Should the gateway return `X-RateLimit-Limit`,
   `X-RateLimit-Remaining`, `X-RateLimit-Reset` on every response (not just 429)?
   This is the standard pattern from GitHub's API and OpenAI's API. Is it right here?

4. **PII redaction notification**: When a prompt is silently redacted, should the user
   know? Options:
   - Silent (current plan) — user never knows
   - Response header: `X-Gateway-Pii-Redacted: true, X-Gateway-Pii-Types: PERSON,SSN`
   - Explicit response field alongside the completion
   What are the privacy implications of telling the user what was redacted?

### Decision required

- Error response schema with `suggestions` field
- Rate limit response headers (429 only vs. every response)
- `Retry-After` calculation
- PII redaction notification approach

## Gap 4: `GET /v1/me` — No Self-Service Visibility

### What's missing

A user has no way to know, without asking an admin:
- What their current roles are
- What models they are allowed to use
- What their rate limit is and how much they've used
- What their tenant's PII policy is (redact vs. block)

This forces admin involvement for basic questions and makes the gateway opaque to its users.

### What needs to be researched

1. **`GET /v1/me` response schema**: What should this endpoint return?
   Proposed fields: `user_id`, `tenant_id`, `roles`, `allowed_models[]`,
   `rate_limit` (limit, used, resets_at), `pii_policy` (action, entities).

2. **Allowed models computation**: Should this be computed by asking OPA (query "what models
   would this user be allowed to use?") or by enumerating the model list and filtering?
   OPA supports partial evaluation which can answer this, but it adds complexity.

3. **Rate limit current usage**: The sliding window data is in Redis. Is exposing the current
   count safe? Does it enable gaming the rate limiter?

### Decision required

- `GET /v1/me` response schema
- Whether allowed models are computed via OPA partial evaluation or enumeration + filter
- Whether to expose current rate limit usage in the response

## Gap 5: Mock Provider Mode — No Offline Testing

### What's missing

The plan has no mock provider mode. Every end-to-end test requires a real API key for at
least one provider. This means:
- Portfolio reviewers cannot run the demo without providing their own API keys
- CI/CD integration tests cannot run without secrets
- Developers cannot test governance features (PII redaction, OPA blocking) in isolation
  from the actual LLM response

### What needs to be researched

1. **Mock provider pattern**: What does a mock OpenAI provider look like? Options:
   - A `mock` provider that returns a canned response (fast, simple)
   - A recorded response library (like VCR for HTTP — record real responses, replay them)
   - A local model via Ollama (real model, no API key needed, but requires Ollama)
   What do other LLM gateway projects use for testing?

2. **`OPENAI_API_KEY=mock` convention**: Should the gateway detect a sentinel value
   and activate mock mode automatically? Is this a recognized pattern?

3. **Test fixture data**: What canned requests and responses should ship with the project
   to make governance testing possible without real providers?
   - A request containing PII (to test redaction)
   - A request containing a jailbreak phrase (to test harm detection)
   - A request from a user without tier2 access to a tier2 model (to test OPA)

### Decision required

- Mock provider implementation approach
- Whether mock mode is activated by sentinel API key or separate env flag
- What test fixtures ship with the project

## Gap 6: Audit Log Retention and Access Control Policy

### What's missing

The plan specifies the audit log schema and that it's append-only with an INSERT-only Postgres
role. It does not define:
- Who can read the audit log (`GET /v1/audit`) — all admins? only the requesting user's
  own records? tenant-scoped?
- Retention period — how long are records kept?
- GDPR right-to-erasure handling — if a user requests deletion, the log contains their
  `user_id`. The plan suggests pseudonymization but doesn't define the mechanism.
- Whether tenants can access their own audit logs vs. only platform admins

### What needs to be researched

1. **Audit log access model**: Should `GET /v1/audit` return only the calling user's records
   (scoped by `user_id`) by default? Should tenant admins see all records for their tenant?
   Should platform admins see everything? How is this enforced — in OPA? In the query?

2. **Retention policy**: What are the relevant regulatory minimums?
   - HIPAA: 6 years
   - GDPR Article 30: duration of processing + 3 years (approximately)
   - SOC 2: 1 year
   How does the monthly partition scheme support retention enforcement?

3. **GDPR erasure**: The plan mentions storing a pseudonymized `user_id` with a
   `user_pseudonym_map` that can be cleared. What does this table look like? How does
   the erasure workflow operate without modifying the append-only audit log?

4. **Audit log export**: Do tenants need to export their audit records (for their own
   compliance reporting)? Should `GET /v1/audit` support CSV or JSONL export?

### Decision required

- Audit log read access model (user-scoped vs. tenant-scoped vs. admin-only)
- Retention enforcement mechanism (scheduled job, partition drop policy)
- GDPR pseudonymization schema and erasure workflow
- Whether export formats are supported in v1

## Resolution Index (2026-05-26)

For full reasoning, see the plan's "Pre-Build Gap Resolutions (2026-05-26)" section.

| Gap | Resolution (one-line) |
|---|---|
| 1. User provisioning IaC | `config/tenants.yaml` + `config/users.yaml` reconciled by `scripts/provision.py`; bootstrap admin gated by `bootstrap_state` table (not "no admin row"); key printed once to stdout; roles emitted as OPA data documents picked up via `--watch` |
| 2. Provider routing | Hybrid: per-provider-scoped `X-Gateway-Provider` permission → `models.yaml` → prefix inference → tenant default → 400. **Provider resolution moves BEFORE `/inspect`** so OPA evaluates the resolved provider. `GET /v1/models` is OPA-filtered. |
| 3. Error/rate-limit/PII headers | OpenAI-shape error with `violations[]`/`required_roles`/`entity_types_detected` (types only, no offsets, no current_roles); mirror OpenAI's `x-ratelimit-*` headers on every response; `Retry-After` + `retry-after-ms`; `X-Gateway-Pii-Redacted` header by default with tenant opt-out |
| 4. `GET /v1/me` | Returns roles, allowed_models (enumerate-and-filter via OPA, not partial-eval), rate_limit incl. current usage, pii_policy. ISO 8601 timestamps. |
| 5. Mock provider | First-class `proxy/app/providers/mock.py` adapter; activated by `MOCK_PROVIDERS=true` or `OPENAI_API_KEY=mock`; 6 canned scenarios in `tests/fixtures/mock_scenarios.py` |
| 6. Audit access / retention / GDPR | User-scoped default with OPA-derived `SELF|TENANT|PLATFORM` + Postgres RLS (FORCE; allowlist-validated scope; connection-checkout RESET); native declarative partitioning + `partition_archive_state`; HMAC-SHA256 pseudonyms with `tenant_id` + `erasure_log` proof table; UUIDv7 `audit_id` + HTTP keyset pagination for JSONL export |

**Cross-cutting addition**: binding **"no LiteLLM / OSS gateway dependency"** Design Principle on the plan. The project owns provider routing, adapters, and config parsing in-tree to keep its dependency surface small for a system that sits on the security boundary.
